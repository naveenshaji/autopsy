# Autopsy 0.1.36

Concurrent writes can no longer give two memories the same entity id, and `autopsy repair-ids` repairs graphs where they already did.

Entity and edge ids used to be allocated as `max + 1`, read in one query and written in a later one. Two writers running at the same time, such as a session import next to a restore or two worker threads, could take the same id. Edges are created by matching entity ids, so every edge written to or from a shared id afterwards attached to all the nodes that had it: one intended relationship fanned out into two or four. Ids now come from a counter in the database server. A single atomic script raises it to the graph's current maximum and then reserves the next ids, so every process and thread sharing the graph gets distinct ids. A note write reserves its note and episode ids together.

`autopsy repair-ids` prints a plan; `autopsy repair-ids --apply` writes it. The plan groups the relationships around shared ids by the write that created them, keeps the ones consistent with how that writer builds edges, and deletes the copies:

- Session imports only link nodes of one session, and a session to its repository or workspace.
- A passage belongs to its recorded parent.
- Relations match the keys recorded in their fact text.
- A note's source episode dates from the write.
- History points at its recorded target.

Groups no rule can settle are left untouched and reported. Each node of a shared id but one gets a fresh id well above the current maximum, and the ids recorded on its edges are rewritten. `--apply` holds the database guard lock, so other writers wait. It first writes a verified backup of the exact pre-repair state, and it saves a report with every deleted relationship and the old-to-new id mapping under `Diagnostics/`.

The generation guard's snapshot after each write now waits for a background save already running, instead of failing a write that has already been applied.

Run `autopsy repair-ids` once after upgrading. Processes still running an older Autopsy keep allocating the old way until they restart, so restart long-running workers before applying.

Validation: 429 automated tests, including a real embedded-FalkorDB round trip of the repair and a concurrency test of the counter. The counter was also checked across threads and separate processes against a real server. The repair was rehearsed on a copy of a live 12,887-node graph: 414 shared ids, 1,651 fanned-out copies removed, 418 nodes renumbered, nothing unresolved. Node count was unchanged, no shared ids or mismatched edge ids remained, backups before and after validated, and a second plan found nothing to do.
