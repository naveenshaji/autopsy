# Autopsy 0.1.38

Bulk writes no longer save the whole database after every query, and the embedded database server no longer grows to gigabytes of memory.

## One save per operation

The rollback guard advances a generation and runs a synchronous `SAVE` of the whole embedded database after each write. That keeps the file on disk in step with the guard's sidecar, but a `SAVE` of a 43 MB database takes about 170 ms and blocks every other client while it runs. Bulk work issued one per query: a restore saved two to three times per item and once per edge, a note write saved for its node, episode and each edge, and the embedding pass saved once per vector. During a large restore on one machine the server spent 97% of its time saving, imports slowed to about 3 items a second, and the disk wrote about 255 MB/s.

Restores, both session importers, note creation and updates, and the embedding pass now run inside `GuardedFalkorGraph.coalesced_saves()`. Each write still takes the guard lock and checks the generation first, so a rolled-back database is refused exactly as before. The generation advance and `SAVE` run at most once a second, and once more when the operation ends, even if it fails. The lock isn't held between writes, so other writers and slow work in between (such as embedding) aren't blocked. Writes from other threads, and writes outside these operations, still save individually. A write that isn't saved yet is still in the server's memory, and any other writer's save includes it.

## Memory use of the embedded server

FalkorDB runs a pool of query threads, one per core by default. With glibc malloc each thread gets its own arena, and memory freed there is rarely returned to the system: a server that had run for 11 hours held 5.2 GB resident for a 167 MB graph. The embedded server now starts with `MALLOC_ARENA_MAX=2` unless you set it yourself.

## Validation

442 automated tests, including:

- an embedded-FalkorDB restore through the guard that saves at most 3 times, where the same restore without coalescing saves more than 80 times;
- unit tests for nesting, failures, other threads, the disabled guard, and rollback refusal inside an operation.

On a copy of a live 13,000-node database:

- Restoring 300 items took 0.4 s with 1 save, against 85 s with 600 saves before.
- Importing the same 3-exchange Claude Code session took 15 s instead of 34 s end to end. Both include about 15 s of process startup.
- A mixed query workload from 8 threads grew the server from 221 MB to more than 1.45 GB in 3 minutes with the default allocator. With two arenas it held at about 505 MB, at the same throughput.
